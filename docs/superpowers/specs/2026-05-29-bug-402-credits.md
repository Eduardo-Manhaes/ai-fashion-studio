# Diagnóstico e Correção: Bug 402 Payment Required

## Problema

**Sintoma:** Usuário paga assinatura com sucesso no Stripe, mas dashboard retorna 402 (Payment Required) ao tentar gerar foto.

**Fluxo esperado:**
```
1. User cria conta
2. User escolhe plano → cria Stripe Checkout Session
3. User paga → Stripe dispara webhook
4. Webhook cria subscription + quota_usage no banco
5. User vê créditos no dashboard
6. User gera foto → funciona
```

**Fluxo atual (QUEBRADO):**
```
1. ✅ User cria conta
2. ✅ User escolhe plano → cria Stripe Checkout Session
3. ✅ User paga → redireciona para /billing/success
4. ❓ Webhook é chamado? Processa? Cria registros?
5. ❌ Dashboard não mostra créditos
6. ❌ Gerar foto → 402 Payment Required
```

## O Que Já Foi Tentado (e não resolveu)

### Tentativa 1: Fix de timestamps (Commit 2bc840a)
**Problema identificado:** `new Date(null).toISOString()` causava RangeError  
**Solução aplicada:** Função `toSafeISOString()` valida timestamps  
**Resultado:** RangeError resolvido, mas bug 402 persistiu

### Tentativa 2: Fix nome do evento (Commit 2d2c6a7)
**Problema identificado:** Código esperava `invoice.paid` mas Stripe envia `invoice.payment_succeeded`  
**Solução aplicada:** Corrigido nome do evento no switch  
**Resultado:** Evento processado, mas bug 402 persistiu

### Tentativa 3: Fallback para timestamps null (Commit 66b5148)
**Problema identificado:** `current_period_start/end` vinham null, violando NOT NULL constraint  
**Solução aplicada:** Fallback com `??` para usar `Date.now()` se null  
**Resultado:** NOT NULL resolvido, webhook retorna 200, mas bug 402 persistiu

### Tentativa 4: Fix signing secret (Manual no Railway)
**Problema identificado:** Typo no webhook secret (letra 'o' em vez de '0')  
**Solução aplicada:** Usuário corrigiu manualmente no Railway  
**Resultado:** Webhook não rejeita mais assinatura, mas bug 402 persistiu

### Tentativa 5: Criar quota_usage no webhook (Commit f3fdedc)
**Problema identificado:** `handleSubscriptionUpsert()` só criava subscription, não quota_usage  
**Solução aplicada:** Código para criar quota_usage imediatamente após subscription  
**Resultado:** Deploy bem-sucedido, mas bug 402 persistiu

## Por Que As Tentativas Falharam?

**HIPÓTESE PRINCIPAL:** Estamos corrigindo o código do webhook, mas **o webhook nunca é chamado pelo Stripe**.

**Evidências:**
1. Logs do Railway não mostram `POST /api/stripe/webhook` após checkouts de teste
2. Claude Chrome confirmou: "nenhum webhook processado desde o deploy"
3. Usuário faz checkout mas nada é logado no servidor

**Outras hipóteses (menos prováveis):**
- Webhook é chamado mas metadata (user_id, plan_id) está vazia
- Subscription é criada mas RLS bloqueia leitura
- GET /api/me tem bug na query

- [ ] Subscription é retornada?

## Solução Proposta

**Fase 1: Diagnóstico Massivo**
- Adicionar logs em TODOS os pontos críticos
- Criar endpoint de debug que mostra estado completo
- Verificar configuração do Stripe Dashboard
- Simular evento manualmente via Stripe CLI

**Fase 2: Correção Baseada em Evidências**
- Após identificar EXATAMENTE onde falha
- Corrigir o ponto específico
- Validar com teste E2E

**Fase 3: Validação**
- Teste completo signup → checkout → créditos → gerar foto
- Confirmar que TODOS os checkpoints passam

## Requisitos da Solução

1. **Observabilidade total:** Logs em cada etapa do fluxo
2. **Testabilidade:** Poder simular fluxo sem depender de Stripe UI
3. **Validação atômica:** Cada checkpoint deve ser testável independentemente
4. **Rollback seguro:** Se correção falhar, poder reverter facilmente
